# TotemWorkspace AI Development Graph

This document describes the maintained AI-development observability architecture. Earlier migration notes and dual-viewer parity requirements are retired; Flutter is now the sole viewer.

## Goal

The graph should answer four questions without turning model prose into architecture truth:

1. What is the coding runtime doing now?
2. Which Module / Feature / Component / Implementation is involved?
3. What changed after the task?
4. What is the impact radius and which tests verify it?

Architecture remains derived from validated workspace knowledge plus production-code evidence. Agent activity, change state and replay are overlays.

## Maintained surface

**Flutter production root** is the only maintained viewer surface for GitHub Pages and the Local Bridge. The browser JavaScript viewer and `/legacy/` route are retired.

```text
GitHub Pages / Flutter localhost
             │
             │ approved-origin HTTP
             ▼
Local Bridge · 127.0.0.1:18765
             │
     ┌───────┼────────┐
     ▼       ▼        ▼
 Agent    Git/code   Verification
 runtime   index       state
     └───────┼────────┘
             ▼
        sibling Totem repos
```

The Bridge stays loopback-only. Browser-facing payloads must not expose credentials, tokens, absolute local repository paths or unpublished source bodies.

## Graph data contract

`intelligence/code-graph.mjs` owns `buildGraphViewModel()`. It combines two evidence classes that must remain separate:

- **Curated architecture**: modules, Features, dependency contracts, EventBus relationships, external services and Observer providers.
- **Generated implementation evidence**: Components, repository-relative implementation paths, symbols, discovered Tests and shared-capability evidence.

Generated implementation evidence can enrich the graph but cannot create or rewrite curated dependency direction, ownership, optional-integration semantics or Observer protocol ownership.

Persistent published data is generated by:

```text
validated architecture + local code index
                │
                ▼
       buildGraphViewModel()
                │
       ┌────────┴────────┐
       ▼                 ▼
/api/graph-data   viewer_flutter/assets/graph-data.json
       │                 │
       └────────► Flutter Viewer
```

## Prompt visibility toggle

Prompt is an optional control surface, not a product mode.

- `promptEnabled = false`: no prompt input is rendered.
- `promptEnabled = true`: Flutter may submit a prompt to the Local Bridge.
- Prompt state must not disable graph browsing, Agent Activity, Change Intelligence, Verification Graph or Development Replay.
- The browser cannot choose the host executable, cwd, sandbox, model or arbitrary CLI flags.
- No task is considered started until the configured runtime emits actual activity.

## Agent activity event model

The Bridge accepts bounded, normalized activity events with a monotonically increasing sequence and timestamp. Supported semantic coordinates may include module, feature, component, repository-relative file, symbol, relation endpoints, test target, task and orchestration identifiers.

Important event families include:

- task/thread/turn lifecycle
- command/tool lifecycle
- prompt and orchestration events
- feature/file/symbol activity
- dependency traversal
- verification lifecycle
- graph-diff updates
- commit/PR/deployment milestones
- model and usage evidence emitted by the runtime

Planning is not execution evidence. `orchestration_planned`, model hints or predicted agent topology must never be presented as proof that an agent/model actually ran.

## Progressive semantic LOD

Detail is revealed only when needed:

```text
L0 Workspace
L1 Module
L2 Feature
L3 Component / Responsibility
L4 Implementation (file / class)
L5 Symbol (method / field / handler) · planned expansion
```

Additional typed entities may include API/Capability, Test, State, Resource/Data and External Service.

The default published view stays compact. User drill-down, source-location interaction or explicit activity focus can reveal deeper Component and Implementation detail without globally exploding the graph.

## Change Intelligence

Change Intelligence compares before/after semantic graph state and maps Git working-tree changes back to semantic coordinates.

```text
current local code index
  → before semantic snapshot
  → collect sibling-repository Git changes
  → incremental production-code refresh
  → after semantic snapshot
  → semantic entity/relation diff
  → Git path → Module / Feature / Component / Implementation / Test mapping
  → dependency impact propagation
  → .totem-index/change-intelligence.json
```

A method-body-only edit can still identify its semantic owner even when architecture shape does not change. Absolute local paths are never exposed to the browser.

## Verification Graph

Verification policy, discovered tests and live execution evidence are distinct:

- `data/test-matrix.json` defines required verification categories.
- Code-index evidence defines discovered Test entities.
- Runtime events define started/passed/failed state.

A required test is not a passed test. `validated-by` relations may connect reliable Feature/API/capability targets to discovered Tests, while live state can propagate running/failure emphasis to related semantic targets.

## Agent runtime

The Local Bridge uses the shared `intelligence/agent-runtime/` layer when host configuration enables a concrete adapter. Execution is opt-in and defaults off.

Runtime responsibilities include:

- capability/model discovery
- thread/turn lifecycle
- sandbox and graph-owned writable roots
- approval handling
- steering/cancellation
- runtime telemetry and usage evidence
- overlapping-write leases

`intelligence/orchestration-plan.mjs` defines topology-free execution constraints. The runtime decides whether to work directly or delegate, how many workers to use and how to schedule them. Required dependency waves, concurrent-write limits, independent review, validation, security and release constraints remain authoritative.

## Development Replay

Local replay persists bounded activity and graph checkpoints under `.totem-index/`. It reconstructs development state by event sequence without publishing private prompt transcripts as architecture data.

Replay must distinguish live and historical state, preserve task lifecycle across Bridge restarts and keep verification/change snapshots aligned to the selected sequence.

## Repository onboarding

**Repository onboarding** must stay data-driven:

1. add the module record to the workspace registry;
2. CI clones configured active repositories;
3. production-code/resource inventory runs;
4. generic semantic surfaces are inferred;
5. graph data is regenerated;
6. Flutter renders the new module;
7. optional curated Feature metadata can improve naming.

Do not add `if (module.id === "...")` analyzer branches merely because a repository is new. Extend generic inference only when a genuinely new technical pattern appears.

## Security boundaries

- Bridge binds to loopback and rejects non-loopback host binding by default.
- Approved browser origins are explicit.
- Browser requests cannot directly supply shell commands.
- Prompt and activity sizes are bounded.
- Repository paths exposed to the UI are repository-relative.
- Published artifacts contain no credentials, local absolute paths or uncommitted source bodies.
- Runtime write access is constrained by graph-derived ownership and lease policy.
- Unsupported approval transports fail closed rather than bypassing authorization.

## Validation expectations

Changes in this area should keep the following properties regression-tested:

- Flutter remains the sole maintained viewer and production root.
- Local Bridge API/CORS remains loopback/allowlist constrained.
- Prompt visibility is independent from activity/change/verification/replay.
- Progressive LOD preserves stable semantic identity.
- Change Intelligence remains traceable to Git/code evidence.
- Verification requirements remain separate from passed evidence.
- planned orchestration remains separate from actual runtime activity.
- retired browser viewer artifacts are not recreated.
